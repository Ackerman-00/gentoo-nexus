### BLOCKER (owner action required): gpm↔ncurses cycle persists — heal trigger too narrow

Previous run applied a heal block (commit b467d91) whose trigger fires only
when the installed ncurses lacks `gpm`. The stage3 desktop image ships
ncurses WITH gpm (desktop profile global USE) but WITHOUT `abi_x86_32`.
The gaming heredoc adds `abi_x86_32` to both gpm and ncurses, so Portage
schedules binary reinstalls of BOTH (`[binary Rg]`, `ABI_X86="32* (64)"`) →
unsolvable runtime cycle (`gpm→ncurses runtime_slot_op`, `ncurses(+gpm)→gpm
runtime`). Verified live: the trigger stays silent (has gpm) and every build
of the 6 packages fails on the cycle.

**Verified fix (tested in docker):** broaden the trigger in build.yml
(`.github/workflows/build.yml` lines ~636-637) to also fire when installed
ncurses lacks `abi_x86_32`. The existing heal body (ncurses `-gpm` binary →
gpm binary → ncurses `+gpm` source `--buildpkg`) then resolves the cycle;
target `emerge --pretend` no longer reports a circular dep. Documented in
issue #5. **Cannot be pushed by the agent (no workflows scope) — owner must
apply.**
